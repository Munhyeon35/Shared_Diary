# 로컬 우선 스냅샷 동기화 — 설계

2026-09-21

## 왜 바꾸는가

일기가 **우리 폰에 있어야** 한다. 서버는 두 폰 사이에서 데이터를 옮기는 우편함일 뿐,
일기의 주인이 아니다. 시차가 16시간이라 두 폰이 동시에 깨어 있는 일이 없으므로
폰끼리 직접 주고받는 방식(P2P)은 쓸 수 없다. 그래서 서버는 남기되,
**내용을 모르는 서버**로 만든다.

여기서 따라오는 이득:

- 신호가 없어도 읽고 쓸 수 있다
- 서버가 작고 단순해져서 어디든 올릴 수 있다
- 3단계에서 암호화하면 서버가 우리 일기를 **볼 수 없다**
- **기능을 추가할 때 서버를 고치지 않아도 된다** — 지금까지는 UI 기능 커밋
  거의 전부가 `server.js`를 같이 건드렸다

크기는 이유가 아니다. 1년치 일기 글·배치가 0.5MB(압축 0.17MB)라 서버에 전부
쌓아도 문제가 없다. 용량을 차지하는 것은 사진(1년에 약 100MB)이며,
사진은 스냅샷과 분리해 따로 다룬다.

## 지금과 바뀐 뒤

| | 지금 | 바뀐 뒤 |
|---|---|---|
| 일기 원본 | 서버 `data/entries.json` | **폰**(IndexedDB) |
| 폰에 있는 것 | 커플 코드·이름뿐 | 일기 전체 + 사진 |
| 동기화 | 30초마다 전부 다시 받음 | id 비교 후 바뀐 것만 |
| 서버가 하는 일 | 내용을 읽고 검사·병합 | 덩어리 보관, `parent`만 확인 |
| 오프라인 | 못 씀 | 읽고 쓰기 모두 가능 |

## 데이터 모델

### 스냅샷

일기장 전체를 담은 하나의 값. 서버에는 **가장 최신 것 하나만** 둔다.

내용 — 이것만 직렬화해 해시한다:

```json
{
  "v": 3,
  "entries": [ /* 페이지들 */ ],
  "deleted": [ /* 묘비들 */ ]
}
```

함께 싣는 이력 — 해시 대상이 아니다:

```json
{
  "id":     "위 문자열의 SHA-256",
  "parent": "이전 스냅샷의 id (없으면 null)",
  "at":     "2026-09-21T05:00:00.000Z",
  "by":     "moon"
}
```

스냅샷은 **정규화(키 정렬)해 직렬화한 문자열**로 다룬다. 그 문자열을
그대로 SHA-256 한 값이 `id`다.

해시 대상은 **내용뿐**이다 — `{v, entries, deleted}`. `parent`, `at`, `by`는
내용이 아니라 이력이므로 문자열 바깥에 따로 싣는다. 이렇게 해야
**내용이 같으면 id가 같다**는 성질이 생기고, "내가 보탤 것이 있는가"를
id 비교만으로 판단할 수 있다.

서버는 받은 문자열을 해시해 `id`와 맞는지만 본다. **파싱하지 않는다.**
3단계에서 이 문자열이 암호문으로 바뀌어도 검사 방식은 그대로다.

### 페이지

기존 entry 모양을 거의 유지하되, **병합을 위해 `touched`를 추가**한다.

```json
{
  "author": "moon",
  "date": "2026-09-21",
  "items": [ { "k": "text", "by": "moon", ... },
             { "k": "sticker", "by": "yeojin", ... } ],
  "mood": "😊",
  "tz": "Asia/Seoul",
  "createdAt": "...",
  "edits": [ { "at": "...", "tz": "..." } ],
  "touched": {
    "moon":   { "rev": 7, "at": "2026-09-21T05:00:00.000Z" },
    "yeojin": { "rev": 2, "at": "2026-09-20T18:00:00.000Z" }
  }
}
```

- 페이지의 아이템은 전부 `by`(놓은 사람)를 갖는다. `by`가 없는 옛 데이터는
  `author`가 놓은 것으로 본다.
- `touched[A]`는 **A가 이 페이지에서 자기 몫을 마지막으로 바꾼 시점**이다.
- `rev`는 그 사람이 그 페이지를 고칠 때마다 오르는 값이다. 두 폰의 시계가
  어긋나도 안전하도록 **병합은 `rev`로 판단**하고, `at`은 화면 표시용으로만 쓴다.
- `rev`는 **지금까지 본 값 중 가장 큰 것 + 1**로 정한다. 단순히 로컬 카운터를
  쓰면 한 사람이 폰과 노트북에서 번갈아 쓸 때 같은 번호가 두 번 나온다.
  (개발 중에는 실제로 그렇게 쓰게 된다.) 두 기기에서 **동시에 오프라인으로**
  고치면 여전히 같은 번호가 날 수 있고, 그때는 위의 동점 규칙으로 떨어진다.

### 묘비

페이지를 통째로 지운 기록.

```json
{ "author": "moon", "date": "2026-09-05", "rev": 8, "at": "..." }
```

아이템 하나를 지우는 것은 묘비가 필요 없다. 병합이 **그 사람의 아이템 집합을
통째로 새 것으로 교체**하므로, 새 집합에 없으면 지워진 것이다.

묘비는 지우지 않고 계속 쌓아둔다(한 줄이 100바이트 미만이라 무시할 만하다).

## 병합 규칙

두 스냅샷 `A`, `B`를 합쳐 하나를 만든다. 결과는 **어느 쪽을 먼저 놓아도 같아야
한다**(교환법칙). 테스트로 이를 확인한다.

### 페이지

같은 `(author, date)`인 페이지끼리 합친다.

```
결과 페이지의 아이템 =
    각 사람 A에 대해:
        A.touched[X].rev 와 B.touched[X].rev 를 비교해 큰 쪽을 고르고
        그쪽 페이지에서 by === X 인 아이템을 가져온다
    (rev가 같으면 at이 늦은 쪽, 그것도 같으면 직렬화 문자열이 사전순으로
     앞서는 쪽 — 어느 쪽을 먼저 넣어도 같은 답이 나와야 하므로
     "A쪽" 같은 인자 순서에 기대는 규칙은 쓰지 않는다)
    → 사람별로 고른 아이템들을 모두 합친다

touched   = 사람별로 고른 쪽의 값
mood/edits = 페이지 주인(author)의 몫을 고른 쪽에서 가져온다
createdAt = 둘 중 이른 쪽
```

한 사람의 몫은 그 사람만 고치므로, 사람 단위로 최신을 고르면 **충돌이 없다.**
문현이 자기 페이지를 고치는 동안 여진이 그 페이지에 스티커를 붙여도 둘 다 살아남는다.

### 묘비

양쪽 묘비를 합집합으로 모은다. 같은 `(author, date)`면 `rev`가 큰 쪽을 남긴다.

페이지는 **`묘비.rev >= 페이지.touched[author].rev`일 때 결과에서 빠진다.**
지운 뒤 다시 쓰면 `rev`가 더 커지므로 페이지가 되살아난다.

### 모르는 데이터에 관대하게

병합과 렌더링은 **모르는 종류의 아이템을 버리지 않고 그대로 보존**한다.
두 폰의 앱 버전이 다를 때, 옛 앱이 새 기능의 데이터를 지워버리면 안 되기 때문이다.
화면에는 그리지 않되 스냅샷에는 남긴다.

좌표·크기처럼 그릴 때 쓰는 값은 **읽는 쪽에서 범위를 보정**한다(서버가 하던 일).

## 사진

### 이름

파일 이름을 **내용의 SHA-256**으로 바꾼다: `<hex>.jpg`.

- 스냅샷에는 이름만 들어간다
- 같은 사진을 두 번 넣어도 한 번만 저장된다
- 받은 파일이 맞는지 이름으로 검증할 수 있다

### 어디에 있나

| | 보관 |
|---|---|
| 폰 | IndexedDB에 Blob으로. 화면에는 `URL.createObjectURL`로 그린다 |
| 서버 | 파일로. **일기에 남아 있는 한 계속 보관**(백업 역할) |

폰이 화면에 그릴 때 서버를 거치지 않으므로, 사진 URL에 커플 코드를 실어 보내던
방식(`/photos/x.jpg?code=...`)이 없어진다. 동기화 계층만 서버에서 사진을
주고받고, 그때는 헤더로 인증한다.

### 주고받기

```
올릴 때  스냅샷이 참조하는 사진마다 HEAD → 404면 PUT (원본 바이트, base64 아님)
받을 때  스냅샷이 참조하는데 폰에 없는 사진만 GET
정리     PUT에 `keep`(남길 사진 이름 목록)을 함께 보낸다.
         서버는 그 목록에 없는 사진을 지운다 — 본문을 읽지 않고도 정리할 수 있다
```

지운 사진이 나중에 다시 필요해지면(병합으로 되살아난 경우) 가진 쪽이 `HEAD`에서
404를 보고 다시 올린다. 저절로 복구된다.

## 동기화 절차

앱을 열 때, 저장한 뒤, 그리고 앱으로 되돌아올 때 실행한다.

```
1. GET /api/snapshot  (If-None-Match: 내 headId)
      304 → 서버에 새 것 없음
      200 → { id, body }

2. 내려받은 것이 있으면
      merged = merge(로컬, 서버)
      로컬에 저장
      참조하는데 없는 사진 받아오기

3. 내 로컬로 만든 스냅샷 id != 서버 id 이면 (= 내가 보탤 것이 있으면)
      없는 사진 먼저 올리기
      PUT /api/snapshot { parent: 서버 id, id: 새 id, body }
        200 → headId = 새 id, 끝
        409 → 그 사이 상대가 올림. 1번으로 돌아가 다시(최대 5회)
```

**"보탤 것이 있는지"는 따로 표시하지 않고 계산한다** — 로컬 데이터로 스냅샷 id를
만들어 `headId`와 비교한다. 플래그가 어긋날 여지가 없다.

`parent`가 서버의 현재 id와 다르면 서버는 **409와 함께 현재 스냅샷을 돌려준다.**
이것이 없으면 늦게 올린 쪽이 상대의 일기를 조용히 덮어쓴다.

## 서버 API

기존 API는 전부 교체한다.

```
GET  /api/snapshot          200 { id, parent, at, by, body }
                            204  아직 없음
                            304  If-None-Match가 현재 id와 같음

PUT  /api/snapshot          { parent, id, at, by, body, keep: [사진이름...] }
                            200 { id }
                            409 { id, parent, at, by, body }   ← parent가 낡음
                            400                               ← sha256(body) != id

  body 는 **문자열**로 주고받는다. 서버는 그 문자열을 해시해 id와 맞는지만
  확인하고 그대로 저장한다 — 파싱하지 않는다.
  keep 에 없는 사진 파일은 이때 지운다.

HEAD /api/photos/<hex>.<ext>  200 | 404
GET  /api/photos/<hex>.<ext>  200 바이트
PUT  /api/photos/<hex>.<ext>  201 | 400(해시 불일치)
```

인증은 지금처럼 `x-couple-code` 헤더. 사진도 헤더로만 받는다(쿼리 파라미터 없앰).

서버는 **본문을 파싱하지 않는다.** `id`가 본문의 해시와 맞는지만 확인한다.
(3단계에서 본문이 암호문이 되면 이 검사도 암호문 기준으로 그대로 동작한다.)

저장 형태: 커플 하나뿐이므로 `data/snapshot.json`(+ `data/photos/`)로 충분하다.

## 실패했을 때

| 상황 | 동작 |
|---|---|
| 네트워크 없음 | 로컬에 저장하고 끝. 다음 기회에 동기화 |
| 409가 5번 반복 | 멈추고 "동기화 실패, 다시 시도" 표시. 로컬 데이터는 그대로 |
| 사진 받기 실패 | 그 사진만 빈 자리로 표시하고 나머지는 정상. 다음에 다시 시도 |
| 스냅샷 해시 불일치 | 받은 것을 버리고 에러 표시. 로컬을 덮어쓰지 않는다 |
| IndexedDB 사용 불가 | 앱을 열지 못함을 명확히 알린다(조용히 서버 모드로 떨어지지 않는다) |

**로컬 데이터를 지우는 경로는 만들지 않는다.** 병합 결과가 이상해도 기존 것을
덮어쓰기 전에 항상 병합을 거친다.

## 기존 데이터 이전

서버에 일기 3편이 있다. 첫 실행 때 자동으로 옮긴다.

```
폰에 로컬 데이터가 없고 서버에 스냅샷도 없으면
    기존 GET /api/entries 로 한 번 읽어온다
    각 페이지에 touched = { author: {rev:1, at: updatedAt} } 를 채운다
    사진은 기존 이름으로 내려받아 해시를 계산하고, 그 해시 이름으로 다시 저장한다
    스냅샷을 만들어 PUT 한다
```

이전이 끝나면 옛 API는 제거한다. 옛 데이터 파일(`data/entries.json`)은
지우지 않고 남겨 둔다(되돌릴 여지).

## 코드 구조

지금 `public/index.html` 한 파일에 전부 들어 있다. 병합 로직은 **DOM 없이
node에서 그대로 실행돼야** 단위 테스트를 쓸 수 있으므로 분리한다.

```
public/lib/snapshot.js   순수 함수만: 정규화, 해시, 병합, 묘비, 검증
                         DOM·네트워크 의존 없음 → node에서 테스트
public/lib/store.js      IndexedDB 읽기/쓰기, 사진 Blob 보관
public/lib/sync.js       위 절차(가져오기·병합·올리기·사진)
public/index.html        화면. 위 세 모듈을 type="module"로 불러 쓴다
```

`server.js`는 스냅샷·사진 API만 남아 크게 줄어든다.

## 테스트

**병합(가장 중요):** node에서 `snapshot.js`를 직접 불러 검증한다.

- 양쪽이 서로 다른 페이지를 썼을 때 → 둘 다 남는다
- 같은 페이지에 주인이 글을, 상대가 스티커를 → 둘 다 남는다
- 같은 사람이 양쪽에서 같은 페이지를 → rev가 큰 쪽이 이긴다
- 지운 페이지가 되살아나지 않는다
- 지운 뒤 다시 쓴 페이지는 살아난다
- 모르는 종류의 아이템이 보존된다
- `merge(A,B)`와 `merge(B,A)`의 결과가 같다

**프로토콜:** 실제 서버를 띄우고 두 클라이언트를 흉내 내어
푸시/풀 순서를 섞어 실행한다. 특히 **409 후 재시도에서 데이터가 사라지지 않는지**.

**브라우저:** 오프라인에서 쓰고, 온라인이 되면 올라가는지.

## 단계

각 단계는 그 자체로 쓸모가 있고, 중간에 멈춰도 손해가 없다.

**1단계 — 로컬 저장소와 오프라인 읽기**
IndexedDB에 일기를 사본으로 두고 화면을 로컬에서 그린다. 쓰기는 아직 기존 API.
저장소 계층을 먼저 검증한다.

**2단계 — 스냅샷 동기화** (가장 큰 단계)
폰이 원본이 된다. 스냅샷·병합·묘비·사진 해시·새 서버 API·데이터 이전.

**3단계 — 암호화**
커플 코드에서 키를 유도해 본문을 암호화한다. 서버는 볼 수 없게 된다.
1·2단계가 안정된 뒤에 얹는다.

## 이번 범위 밖

- 암호화(3단계)
- 푸시 알림
- 세 명 이상 — `rev`는 사람마다 폰 한 대를 전제한다. 같은 사람이 두 기기에서
  쓰면 `rev`가 충돌한다. 필요해지면 기기 id를 더해야 한다.
- 여러 커플 — 서버는 커플 하나를 전제한다
